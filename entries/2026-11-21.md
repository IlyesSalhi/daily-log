## [Veille] Barracuda ESG : chaîne bypass d'auth + injection de commande exploitée (CVE-2026-116606, CVE-2026-111560)
- Le 10/11/2026, la CISA a ajouté au catalogue KEV deux failles Barracuda exploitées : CVE-2026-116606 (CVSS 9.3), un contournement d'authentification permettant à un attaquant non authentifié de restaurer une sauvegarde de configuration forgée sur Email Security Gateway (< 9.4.0.030), et CVE-2026-111560 (CVSS 8.6), une injection de commande OS via le champ fuseau horaire, exécutée en root.
- Enchaînées, elles donnent une RCE root sans authentification ; Barracuda confirme des attaques contre « un petit nombre d'organisations » et watchTowr a publié du code d'exploitation.
- Pourquoi c'est important : une passerelle mail est en frontière Internet et voit tout le flux de messagerie, c'est une cible de choix pour la persistance.
- À retenir : passer en 9.4.0.030+, ne jamais exposer l'interface d'administration sur Internet, et rechercher des restaurations de configuration inattendues dans les journaux.
- Source : https://securityonline.info/cisa-kev-six-vulnerabilities-november-2026/

## [Note] Linux : les namespaces, brique de base des conteneurs
- Un namespace isole une ressource du noyau pour un groupe de processus : `pid`, `net`, `mnt`, `uts`, `ipc`, `user`, `cgroup`, `time`.
- Un « conteneur » n'est qu'un processus lancé dans un ensemble de namespaces, limité par des cgroups (ressources) et filtré par seccomp/capabilities.
- Le namespace `user` mappe l'UID 0 du conteneur sur un UID non privilégié de l'hôte : root dedans, utilisateur lambda dehors (mode rootless).
- On voit les namespaces d'un processus dans `/proc/<pid>/ns/` ; deux processus partagent un namespace si les inodes sont identiques.
- Exemple : `unshare --user --map-root-user --pid --fork --mount-proc bash` puis `id` et `ps aux` → on est « root » et on ne voit que ses propres processus.
- Pour entrer dans les namespaces d'un conteneur existant : `nsenter -t <pid> -n ip a` (seulement le namespace réseau).
- Côté sécurité : les namespaces isolent mais partagent le même noyau, une faille noyau suffit à s'échapper ; d'où l'intérêt de seccomp, AppArmor/SELinux, ou gVisor/Kata pour les charges non fiables.

## [Note] Git : blobs, trees, commits, ce que stocke vraiment un dépôt
- Git est une base clé-valeur adressée par contenu : chaque objet est identifié par le hash (SHA-1, ou SHA-256 en option) de son type, sa taille et son contenu.
- Quatre types d'objets : `blob` (contenu d'un fichier, sans nom), `tree` (liste nom → blob/tree + mode), `commit` (tree racine, parent(s), auteur, message), `tag` annoté.
- Une branche n'est qu'un fichier contenant le hash d'un commit (`.git/refs/heads/main`), et `HEAD` pointe vers une branche ou directement un commit (« detached HEAD »).
- Modifier un octet change le hash du blob, donc du tree, donc du commit : c'est ce chaînage qui rend l'historique infalsifiable sans réécriture visible.
- Exemple : `git cat-file -p HEAD` affiche le commit, puis `git cat-file -p HEAD^{tree}` le tree, et `git cat-file -t <hash>` le type d'un objet.
- Les objets sont d'abord « loose » (zlib dans `.git/objects/xx/…`), puis regroupés en packfiles delta-compressés par `git gc`.
- Conséquence sécurité : un secret commité reste dans les objets même après suppression du fichier ; il faut réécrire l'historique (`git filter-repo`) et surtout révoquer le secret.
