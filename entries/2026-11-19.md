# 2026-11-19

## [Veille] Puppet Server : RCE exploitée via désérialisation des rapports (CVE-2026-115731)
- Faille de désérialisation dans le traitement des rapports de Puppet Server : tout client muni d'un certificat signé par la CA Puppet peut envoyer (PUT) un rapport avec un type « rich data » forgé et exécuter du code sous l'utilisateur du service. Avec l'autosign activé, un attaquant non authentifié peut obtenir un certificat puis exploiter.
- Touchés : Puppet Enterprise 2023.8.x < 2023.8.13, 2025.x < 2025.12.1, 2026.0.0 ; Puppet Core 8.x < 8.22.2 et 9.x < 9.1.3 ; OpenVox aussi. Ajoutée au catalogue KEV de la CISA (échéance agences fédérales : 1er décembre 2026).
- Enjeu : le serveur de config contrôle toute la flotte et l'exécution sous `puppet` donne accès à la clé de signature de la CA.
- Défense : patcher et redémarrer, désactiver/restreindre l'autosign, ne pas exposer le port 8140, auditer les certificats signés ; en cas de compromission, considérer la CA comme compromise et la reconstruire.
- Source : https://www.helpnetsecurity.com/2026/11/19/puppet-enterprise-vulnerability-cve-2026-115731-exploited/

## [Note] Kerberos : TGT, TGS et ce que contient vraiment un ticket
- Étape AS (Authentication Service) : le client demande un TGT au KDC ; avec la pré-authentification, il chiffre un horodatage avec une clé dérivée de son mot de passe (sans pré-auth → AS-REP roasting possible).
- Le TGT est chiffré avec la clé du compte `krbtgt` : le client ne peut pas le lire, il ne fait que le présenter. Qui détient la clé krbtgt peut forger des TGT (Golden Ticket).
- Étape TGS : avec son TGT, le client demande un ticket de service pour un SPN (ex. `HTTP/web.example.com`). Ce ticket est chiffré avec la clé du compte de service → un attaquant peut le casser hors ligne si le mot de passe est faible (Kerberoasting).
- Le service déchiffre le ticket avec sa clé (keytab) et récupère la clé de session et l'identité du client (PAC côté AD) sans contacter le KDC.
- Les horloges doivent être synchronisées (tolérance par défaut 5 min) à cause des authenticators horodatés.
- Exemple (MIT/FreeIPA) :
  `kinit alice@EXAMPLE.COM && kvno HTTP/web.example.com && klist -e`
  → `klist -e` montre le TGT `krbtgt/EXAMPLE.COM@EXAMPLE.COM`, le ticket de service et les types de chiffrement (préférer aes256-cts, bannir RC4).

## [Note] Linux : les capabilities plutôt que root ou setuid
- Le noyau découpe les privilèges de root en capabilities indépendantes : `CAP_NET_BIND_SERVICE` (ports < 1024), `CAP_NET_RAW` (sockets brutes), `CAP_SYS_ADMIN` (fourre-tout, quasi équivalent à root), `CAP_DAC_READ_SEARCH` (contourner les droits de lecture)…
- Chaque processus a plusieurs ensembles : permitted, effective, inheritable, bounding et ambient ; visibles dans `/proc/<pid>/status` (CapPrm, CapEff, CapBnd…).
- On peut attribuer des capabilities à un binaire (attributs étendus) au lieu du bit setuid :
  `sudo setcap cap_net_bind_service=+ep /usr/local/bin/monserveur` puis `getcap /usr/local/bin/monserveur`
- Décoder un masque : `capsh --decode=$(awk '/CapEff/{print $2}' /proc/self/status)`
- Côté audit/escalade : `getcap -r / 2>/dev/null` liste les binaires dotés de capabilities ; `cap_setuid` ou `cap_dac_override` sur un interpréteur (python, perl) = élévation de privilèges triviale.
- Côté systemd : `CapabilityBoundingSet=` et `AmbientCapabilities=` permettent de lancer un service non-root avec juste la capability nécessaire.
