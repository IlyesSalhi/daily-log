# 2026-11-26

## [Veille] Idunno.AntiCsrf (ASP.NET) : RCE non authentifiée exploitée, sans correctif (CVE-2026-131914)
- Module IHttpModule anti-CSRF pour WebForms, abandonné depuis 2008 (versions 0.9.1.0 / 0.9.1 Beta) : il désérialise le jeton CSRF avec un `ObjectStateFormatter` sans MAC ni signature, d'où une RCE dans w3wp.exe via une seule requête POST (CVSS 9.3).
- Exploitation active signalée par Mandiant, sondes observées par watchTowr le 24/11 ; ajoutée au KEV de la CISA le 24/11/2026.
- Aucun correctif prévu : de vieilles applis internes peuvent embarquer cette DLL sans que personne ne s'en souvienne.
- Défense : chercher `Idunno.AntiCsrf`/`AntiCsrfModule` dans les Web.config et bin/, migrer vers `System.Web.Helpers.AntiForgery` ou IAntiforgery ; en cas de compromission, faire tourner le machineKey et les secrets.
- Source : https://thehackernews.com/2026/11/hackers-exploit-critical-aspnet-anti.html

## [Veille] Xen Orchestra : prise de session admin avec un cookie JSON vide (CVE-2026-133469)
- xo-server accepte un objet JSON vide comme jeton de session : le magasin de jetons l'interprète comme une recherche sans filtre et renvoie le premier jeton valide, souvent celui d'un admin (CVSS 9.8, CWE-287).
- Ajoutée au KEV de la CISA le 25/11/2026 ; des détails d'exploitation sont publics (GHSA-2r3w-c2vx-fv5g).
- Impact : contrôle de l'orchestrateur, donc root sur les hôtes XCP-ng gérés.
- Défense : passer en xo-server 5.213.1 ou 5.211.2 et ne jamais exposer l'interface d'admin d'un hyperviseur hors d'un réseau d'administration dédié.
- Source : https://securityonline.info/cisa-kev-catalog-micollab-juniper-danfoss/

## [Note] Web : JWT et la confusion d'algorithme
- Un JWT = `header.payload.signature` en base64url ; le header indique l'algorithme (`alg`) utilisé pour la signature.
- Attaque `alg: none` : si la bibliothèque fait confiance au header, un jeton non signé est accepté.
- Confusion RS256 → HS256 : le serveur vérifie avec sa clé publique RSA ; si l'attaquant passe `alg` à HS256, certaines libs utilisent cette clé publique (connue de tous) comme secret HMAC, et l'attaquant peut forger n'importe quel jeton.
- Correctif : fixer côté serveur la liste des algorithmes autorisés, ne jamais la lire depuis le jeton.
- Exemple (PyJWT) : `jwt.decode(token, pubkey, algorithms=["RS256"], audience="api")`.
- Décoder un jeton pour l'inspecter : `cut -d. -f1 <<<"$T" | base64 -d 2>/dev/null`.
- Lab utile : PortSwigger Web Security Academy, rubrique « JWT attacks ».

## [Note] FreeIPA : restreindre les connexions avec les règles HBAC
- HBAC (Host-Based Access Control) décide qui peut se connecter à quel hôte via quel service PAM (sshd, sudo, login…). L'évaluation est faite par SSSD sur le client.
- Par défaut, la règle `allow_all` autorise tout le monde partout : la première étape d'un durcissement est de la désactiver.
- Une règle associe utilisateurs/groupes, hôtes/groupes d'hôtes et services/groupes de services.
- Exemple :
  `ipa hbacrule-add admins_ssh && ipa hbacrule-add-user admins_ssh --groups=admins`
  `ipa hbacrule-add-host admins_ssh --hostgroups=serveurs && ipa hbacrule-add-service admins_ssh --hbacsvcs=sshd`
  `ipa hbacrule-disable allow_all`
- Tester avant d'appliquer : `ipa hbactest --user=alice --host=web01.example.com --service=sshd`.
- Côté client, un refus apparaît dans `/var/log/sssd/` et le journal d'auth (`pam_sss ... Permission denied`).

## [Note] Linux : seccomp, filtrer les appels système d'un processus
- seccomp permet à un processus de restreindre les syscalls qu'il (et ses enfants) pourra faire ; le mode filtre utilise un programme BPF qui renvoie ALLOW, ERRNO, KILL ou LOG.
- Le filtre est irréversible et hérité : idéal pour réduire la surface d'attaque du noyau exposée à un service.
- Docker applique un profil par défaut qui bloque une quarantaine de syscalls dangereux (ex. `kexec_load`, `open_by_handle_at`).
- Avec systemd, sans écrire de BPF :
  `[Service]` puis `SystemCallFilter=@system-service` et `SystemCallErrorNumber=EPERM`
- Voir les groupes disponibles : `systemd-analyze syscall-filter @system-service`.
- Vérifier qu'un processus est filtré : `grep Seccomp /proc/<PID>/status` (2 = mode filtre).
- `systemd-analyze security <unité>` donne un score d'exposition et suggère d'autres options de durcissement.

## [Note] Réseau : un pare-feu « drop par défaut » minimal avec nftables
- nftables remplace iptables : une seule syntaxe pour IPv4/IPv6 (famille `inet`), des sets natifs et des mises à jour atomiques.
- Principe : politique `drop` en entrée, puis on autorise explicitement le trafic établi, la boucle locale et les services voulus.
- Exemple `/etc/nftables.conf` :
  `table inet filter { chain input { type filter hook input priority 0; policy drop;`
  `  ct state established,related accept; ct state invalid drop; iif lo accept;`
  `  meta l4proto { icmp, ipv6-icmp } accept; tcp dport 22 ip saddr 10.0.0.0/24 accept; } }`
- Garder ICMPv6 : sans lui, la découverte de voisins et le PMTU cassent en IPv6.
- Tester sans se couper l'accès : `nft -c -f /etc/nftables.conf` (vérification de syntaxe) puis appliquer depuis une console hors bande.
- Lister l'état : `nft list ruleset`.

## [Note] Git : retrouver un commit « perdu » avec le reflog
- Le reflog enregistre localement chaque déplacement de HEAD et des branches (commit, reset, rebase, checkout), même quand le commit n'est plus référencé par aucune branche.
- Après un `git reset --hard` ou un rebase raté, le travail n'est donc pas perdu tant que le garbage collector n'est pas passé (90 jours par défaut pour les entrées accessibles, 30 pour les inaccessibles).
- Exemple :
  `git reflog` → repérer la ligne `HEAD@{3}: commit: ajout du parseur`
  `git branch sauvetage HEAD@{3}` ou `git reset --hard HEAD@{3}`
- Le reflog est propre à chaque clone : il n'est jamais poussé, et un clone neuf n'en a pas.
- En dernier recours : `git fsck --lost-found` liste les objets orphelins.
- Côté sécurité : un secret « effacé » par reset reste récupérable localement ; s'il a été poussé, il faut le révoquer, pas seulement réécrire l'historique.
